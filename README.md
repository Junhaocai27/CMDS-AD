# CMDS-AD: Cross-Modal Dual-Stream Decoupling for Few-Shot Anomaly Detection

[![arXiv](https://img.shields.io/badge/arXiv-2606.20300-b31b1b.svg)](https://arxiv.org/abs/2606.20300)
[![Project Page](https://img.shields.io/badge/Project-Page-blue.svg)](https://cmds-ad.github.io/)
[![ECCV 2026](https://img.shields.io/badge/ECCV-2026-4b2e83.svg)](https://eccv.ecva.net/)

Official code release for CMDS-AD, a cross-modal few-shot anomaly detection
framework for 3D industrial inspection. The release covers the complete
pipeline used in the paper:

1. dataset conversion and preprocessing;
2. real surface-normal generation from the dataset geometry;
3. category-specific LoRA training;
4. Stable Diffusion image-to-image (i2i) RGB generation;
5. Marigold estimated-normal inference for both original and generated RGB;
6. foreground-mask generation;
7. dual-direction cross-modal training; and
8. anomaly-map fusion and evaluation.

The repository is source-only. Datasets, diffusion checkpoints, Marigold
checkpoints, LoRA files, feature-extractor weights, and final CMDS-AD
checkpoints are intentionally not stored in Git.

The trained weights and the external diffusion-model assets can be downloaded
from the following archive:

<https://drive.google.com/file/d/1CNmmkdtiumA47AJ1PoZ4klwAyvFbvvYq/view?usp=sharing>

After downloading, extract the archive so that the release contains the
following logical directories:

```text
weights/stable-diffusion-2-1-base/
weights/marigold/
weights/lora_mvtec/<class>/final_lora.safetensors
weights/lora_eyecandies/<class>/final_lora.safetensors

```

The archive may contain checkpoints produced by an earlier internal naming
convention. The inference scripts accept both the clean names generated by
this release and those legacy directory names; no checkpoint contents need to
be changed.

The repository does not upload Stable Diffusion, Marigold, DINO, PointMAE,
or CMDS-AD model weights. Please respect the licenses of all downloaded and
third-party models.

## 🧰 Environment

The code is intended for Linux with CUDA. Python 3.10 is recommended. Install
a PyTorch/torchvision pair compatible with the CUDA driver before installing
the remaining packages.

```bash
git clone https://github.com/Junhaocai27/CMDS-AD.git
cd CMDS-AD

conda create -n cmds-ad python=3.10 -y
conda activate cmds-ad
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

The foreground-mask stage uses `pointnet2_ops`. Install a version compatible
with the selected PyTorch and CUDA toolchain, for example:

```bash
git clone https://github.com/erikwijmans/Pointnet2_PyTorch.git
python -m pip install -e Pointnet2_PyTorch/pointnet2_ops_lib
```

The DINO image backbone is loaded through `timm`. If its pretrained weights
are not already cached, the first feature-extraction run downloads them from
Hugging Face.

## 🧪 Dataset preparation

Download [MVTec 3D-AD](https://www.mvtec.com/research-teaching/datasets/mvtec-3d-ad)
and Eyecandies from their official sources. Do not run the MVTec preprocessing
script directly on the only copy of the raw data: it updates XYZ TIFF files
in place. Keep the downloaded data under `data/raw/` and preprocess a working
copy.

### 🔷 MVTec 3D-AD

```bash
mkdir -p data/derived
cp -a data/raw/mvtec_3d data/derived/mvtec_3d
python processing/preprocess_mvtec3dad.py \
  --dataset_path data/derived/mvtec_3d
```

The converted MVTec tree must contain, for every category and split, folders
such as:

```text
data/derived/mvtec_3d/bagel/train/good/rgb/
data/derived/mvtec_3d/bagel/train/good/xyz/
data/derived/mvtec_3d/bagel/test/<defect>/rgb/
data/derived/mvtec_3d/bagel/test/<defect>/xyz/
data/derived/mvtec_3d/bagel/test/<defect>/gt/
```

The `gt/` directory is part of the test-set annotation contract and must be
retained when the dataset is copied or preprocessed. It contains the
pixel-level anomaly ground-truth mask for each anomalous test image. The
`good` test split is normal by definition, so it may not contain an explicit
mask file; such images are evaluated with an all-zero anomaly mask.

### 🍬 Eyecandies

```bash
python processing/preprocess_eyecandies.py \
  --dataset_path data/raw/Eyecandies \
  --target_dir data/derived/eyecandies_mvtec_format
```

The conversion creates the MVTec-like RGB, XYZ, ground-truth, and normal
layouts consumed by the remaining scripts.

### 🏷️ Dataset annotations

Both datasets use two different kinds of masks, and they must not be
interchanged:

- **Anomaly ground truth** is the dataset annotation used only for test
  evaluation. For MVTec 3D-AD, the expected location is
  `data/derived/mvtec_3d/<class>/test/<defect>/gt/<stem>.png`. A directory
  named `ground_truth/<defect>/` is also accepted by the annotation validator
  for converted layouts. Every image in a non-`good` test defect directory
  must have a corresponding ground-truth mask.
- **Image-level labels** are determined by the test directory name:
  `test/good` is normal and every other defect directory is anomalous. A
  normal `good` image without an explicit mask is treated as an all-zero
  pixel label.
- **Foreground masks** are generated by `mask_vis_mvtec3dad.py` and
  `mask_vis_eyecandies.py`. The resulting trees, such as
  `data/derived/mvtec_3d_masks_generated/`, describe the visible object
  foreground and are used by the real stream, masked loss, and inference
  foreground constraint. They are not anomaly ground truth and must not be
  used to calculate anomaly metrics.

The MVTec preprocessing script updates XYZ TIFF files in the working copy
only. It does not rewrite, regenerate, or delete
`test/<defect>/gt/` annotation files. Keep the original test annotations when
creating `data/derived/mvtec_3d`; copying only RGB and XYZ files is
insufficient for evaluation.

The repository does not redistribute MVTec 3D-AD or Eyecandies data. Obtain
the datasets from their official sources, including the MVTec test-set
annotations, and then audit the converted trees before running the model:

```bash
python scripts/validate_dataset.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --splits test

python scripts/validate_dataset.py \
  --dataset eyecandies \
  --dataset_root data/derived/eyecandies_mvtec_format \
  --splits test
```

The validator reports the total image count, anomalous image count, and
matched anomaly-mask count, and fails if any anomalous image is missing its
mask. With the complete converted datasets, the expected test-set totals are
1,197 images / 948 anomalous images for MVTec 3D-AD and 500 images / 240
anomalous images for Eyecandies. These totals are an annotation audit, not a
requirement to run all categories during development.

## 🔄 Complete data-generation pipeline

The commands below use MVTec as an example. Replace `mvtec` with `eyecandies`
and use the corresponding `*_eyecandies` scripts and roots for the second
dataset.

The default category list contains all ten categories. To validate only a few
categories, set `CMDS_AD_CLASSES`, for example:

```bash
export CMDS_AD_CLASSES="bagel carrot"
export CMDS_AD_GPUS="0,1"
```

`CMDS_AD_GPUS` is a comma-separated list. The workers distribute categories
across the listed devices. Set it to `0` on a single-GPU system.

### 1️⃣ Prepare original RGB images

This creates the flat RGB tree used by LoRA, i2i, Marigold, and the CMDS-AD
training datasets. At this point it contains one original RGB image per
training sample.

```bash
python scripts/prepare_rgb.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --output_root data/derived/output_generation_full
```

For Eyecandies:

```bash
python scripts/prepare_rgb.py \
  --dataset eyecandies \
  --dataset_root data/derived/eyecandies_mvtec_format \
  --output_root data/derived/output_generation_eyecandies
```

### 2️⃣ Train category-specific LoRA modules

The LoRA stage uses the original training RGB images and writes one
`final_lora.safetensors` per category.

```bash
export CMDS_AD_SD_MODEL="$PWD/weights/stable-diffusion-2-1-base"
export CMDS_AD_MVTEC_ROOT="$PWD/data/derived/mvtec_3d"
export CMDS_AD_MVTEC_LORA_ROOT="$PWD/weights/lora_mvtec"
python scripts/train_lora_mvtec3dad.py
```

For Eyecandies:

```bash
export CMDS_AD_EYECANDIES_ROOT="$PWD/data/derived/eyecandies_mvtec_format"
export CMDS_AD_EYECANDIES_LORA_ROOT="$PWD/weights/lora_eyecandies"
python scripts/train_lora_eyecandies.py
```

The release preserves the paper settings used by the original LoRA stage,
including 512-pixel training, batch size 1, gradient accumulation, textual
inversion, and 1,000 textual-inversion/LoRA tuning steps. Reduce the step
counts only for a smoke test; reduced-step outputs must not be used for the
reported experiments.

### 3️⃣ Generate additional RGB images with Stable Diffusion i2i

The i2i stage copies each original RGB into the output directory and creates
five deterministic images with seeds `42`, `1024`, `2023`, `8888`, and
`12345`. The default strength is `0.2`, guidance scale is `4`, and the number
of diffusion steps is `50`.

```bash
export CMDS_AD_MVTEC_RGB_ROOT="$PWD/data/derived/output_generation_full"
python scripts/generate_rgb_mvtec3dad.py
```

For Eyecandies:

```bash
export CMDS_AD_EYECANDIES_RGB_ROOT="$PWD/data/derived/output_generation_eyecandies"
python scripts/generate_rgb_eyecandies.py
```

After this stage, a typical MVTec category contains:

```text
data/derived/output_generation_full/<class>/000.png
data/derived/output_generation_full/<class>/000_seed42.png
data/derived/output_generation_full/<class>/000_seed1024.png
...
```

### 4️⃣ Generate real normals from dataset geometry

Real normals are computed from the preprocessed XYZ point clouds with the
Open3D CUDA estimator. The pipeline removes the supporting plane and isolated
components, estimates and orients normals, maps them to RGB, pads to a square,
and resizes to `224 x 224`. The default estimator parameters are
`radius=0.01` and `max_nn=30`.

Generate training real normals:

```bash
python scripts/generate_real_normals.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --output_root data/derived/normal_output_train_new_full/real_normals \
  --splits train \
  --device cuda
```

Generate test real normals for inference:

```bash
python scripts/generate_real_normals.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --output_root data/derived/normal_output_mv_format_infer/real_normals \
  --splits test \
  --device cuda
```

For Eyecandies, the corresponding script copies the dataset-provided normal
maps when available and uses the same CUDA conversion for XYZ-only samples:

```bash
python scripts/generate_real_normals.py \
  --dataset eyecandies \
  --dataset_root data/derived/eyecandies_mvtec_format \
  --output_root data/derived/normal_output_train_eyecandies/real_normals \
  --splits train test \
  --device cuda
```

### 5️⃣ Generate estimated normals with Marigold

Marigold is applied to every original and LoRA-generated training RGB. The
same estimator is applied to the original test RGB images. The release uses
the following reproducible settings: `denoise_steps=10`, `ensemble_size=10`,
`seed=42`, the checkpoint's default processing resolution, full precision,
and batch size 1.

Training estimated normals:

```bash
python scripts/generate_estimated_normals.py \
  --dataset mvtec \
  --rgb_root data/derived/output_generation_full \
  --output_root data/derived/normal_output_train_new_full/estimated_normals \
  --checkpoint weights/marigold \
  --splits train \
  --batch_size 1 \
  --seed 42 \
  --denoise_steps 10 \
  --device cuda
```

Test estimated normals:

```bash
python scripts/generate_estimated_normals.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --output_root data/derived/normal_output_mv_format_infer/estimated_normals \
  --checkpoint weights/marigold \
  --splits test \
  --batch_size 1 \
  --seed 42 \
  --denoise_steps 10 \
  --device cuda
```

For Eyecandies, use `--dataset eyecandies` and the corresponding generated-RGB,
dataset, and output roots. Both the original RGB and every generated RGB must
have a matching estimated-normal file.

### 6️⃣ Generate foreground masks

The mask stage uses the multimodal feature extractor and the PointNet2
operators. Use batch size 1 on a 24 GB GPU if necessary.

```bash
python mask_vis_mvtec3dad.py \
  --dataset_path data/derived/mvtec_3d \
  --save_dir data/derived/mvtec_3d_masks_generated \
  --class_name all \
  --batch_size 1
```

For Eyecandies:

```bash
python mask_vis_eyecandies.py \
  --dataset_path data/derived/eyecandies_mvtec_format \
  --save_dir data/derived/eyecandies_masks_generated \
  --class_name all \
  --batch_size 1
```

## 🧠 Training CMDS-AD

The training dataset deliberately combines the two RGB streams:

- the real stream uses the original dataset RGB, its real normal, and the
  foreground mask;
- the estimated stream uses the original and generated RGB images together
  with their Marigold estimated normals;
- generated-image stems are matched to the original stem for real-normal and
  mask lookup;
- the 2D-to-3D and 3D-to-2D directions are trained independently with the same
  dual-stream loss and then used together at inference.

The launcher maps shots to the released training schedule:

| shots | default training steps |
|---:|---:|
| 1 | 3000 |
| 2 | 1500 |
| 4 | 750 |

### 🖥️ Original high-memory configuration

This reproduces the original paper-scale training configuration used on the
32 GB-class GPU deployment. It uses batch size 2 and should be run on a GPU
with sufficient memory (approximately 32 GB for the released model and data
flow). This is the command corresponding to the original high-memory
experiments.

```bash
python scripts/train.py \
  --dataset mvtec \
  --classes bagel carrot cookie \
  --shots 1 2 4 \
  --directions both \
  --batch_size 2 \
  --device cuda \
  --checkpoint_root checkpoints \
  --wandb_mode disabled
```

Replace `bagel carrot cookie` with all MVTec categories for the complete
experiment. The same command works for Eyecandies with
`--dataset eyecandies` and its category names.

### 💾 24 GB GPU configuration

On a 24 GB GPU, use batch size 1. This is the command corresponding to the
validated 24 GB deployment. It is the only memory adaptation required by the
release; the model architecture, data flow, loss, optimizer schedule, and
inference logic are unchanged.

```bash
python scripts/train.py \
  --dataset mvtec \
  --classes bagel carrot cookie \
  --shots 1 2 4 \
  --directions both \
  --batch_size 1 \
  --device cuda \
  --checkpoint_root checkpoints \
  --wandb_mode disabled
```

To train one direction only, set `--directions 2dto3d` or
`--directions 3dto2d`. Use `--max_steps` only when intentionally overriding
the shot-dependent schedule.

## 🔍 Inference and evaluation

Before inference, make sure that the test RGB, test real normals, test
estimated normals, and test masks have matching stems and directory layouts:

```text
data/derived/mvtec_3d/<class>/test/<defect>/rgb/<stem>.png
data/derived/mvtec_3d/<class>/test/<defect>/gt/<stem>.png
data/derived/normal_output_mv_format_infer/real_normals/<class>/test/<defect>/<stem>.png
data/derived/normal_output_mv_format_infer/estimated_normals/<class>/test/<defect>/normals_vis/<stem>_normals.png
data/derived/mvtec_3d_masks_generated/<class>/test/<defect>/<stem>.png
```

The inference code uses the original test RGB as the image input, both real
and estimated normal streams, and the foreground mask. The generated RGB
images are used to enlarge the few-shot training stream; they are not used as
substitutes for test images.

### 🖥️ Original high-memory inference command

The original configuration can use a larger inference batch when memory is
available:

```bash
python test_anomaly_fusion_mvtec3dad.py \
  --dataset_root data/derived/mvtec_3d \
  --real_normal_root data/derived/normal_output_mv_format_infer/real_normals \
  --est_normal_root data/derived/normal_output_mv_format_infer/estimated_normals \
  --mask_root data/derived/mvtec_3d_masks_generated \
  --ckpt_root_3d2d checkpoints/checkpoints_dual_3dto2d \
  --ckpt_root_2d3d checkpoints/checkpoints_dual_2dto3d \
  --ckpt_suffix _1shot \
  --classes bagel carrot cookie \
  --batch_size 2 \
  --wandb_mode disabled
```

### 💾 24 GB GPU inference command

Use batch size 1 on a 24 GB GPU:

```bash
python test_anomaly_fusion_mvtec3dad.py \
  --dataset_root data/derived/mvtec_3d \
  --real_normal_root data/derived/normal_output_mv_format_infer/real_normals \
  --est_normal_root data/derived/normal_output_mv_format_infer/estimated_normals \
  --mask_root data/derived/mvtec_3d_masks_generated \
  --ckpt_root_3d2d checkpoints/checkpoints_dual_3dto2d \
  --ckpt_root_2d3d checkpoints/checkpoints_dual_2dto3d \
  --ckpt_suffix _1shot \
  --classes bagel carrot cookie \
  --batch_size 1 \
  --wandb_mode disabled
```

Use `--max_samples 1` for a one-image smoke test. Remove it for reported
metrics. The second command intentionally changes only the batch size.

For Eyecandies, run `test_anomaly_fusion_eyecandies.py` with the converted
dataset, Eyecandies normal, mask, and checkpoint roots.

## 📋 Expected data contract

For each training category, the normal and mask trees should have the
following form:

```text
data/derived/output_generation_full/<class>/
data/derived/normal_output_train_new_full/real_normals/<class>/train/good/
data/derived/normal_output_train_new_full/estimated_normals/<class>/train/good/normals_vis/
data/derived/mvtec_3d_masks_generated/<class>/train/good/
```

For MVTec test evaluation, retain the RGB, XYZ, and anomaly-annotation trees:

```text
data/derived/mvtec_3d/<class>/test/good/rgb/
data/derived/mvtec_3d/<class>/test/good/xyz/
data/derived/mvtec_3d/<class>/test/<defect>/rgb/
data/derived/mvtec_3d/<class>/test/<defect>/xyz/
data/derived/mvtec_3d/<class>/test/<defect>/gt/
```

The first tree contains one original RGB plus five generated RGB images per
base image. Estimated normals contain one file for every RGB image. Real
normals and masks are indexed by the base image stem and reused for the
generated variants. Missing normal or mask files should be treated as a data
preparation error rather than silently replaced with all-foreground masks.

## ✅ Validation

The source-only checks do not download models or start a full experiment:

```bash
python scripts/validate_release.py
python -m compileall -q .
python scripts/validate_dataset.py \
  --dataset mvtec \
  --dataset_root data/derived/mvtec_3d \
  --splits test
python scripts/validate_dataset.py \
  --dataset eyecandies \
  --dataset_root data/derived/eyecandies_mvtec_format \
  --splits test
python scripts/train.py \
  --dataset mvtec --classes bagel --shots 1 --directions both --dry-run
python scripts/generate_estimated_normals.py \
  --dataset mvtec --classes bagel --checkpoint weights/marigold --dry-run
```

For a real GPU validation, run one LoRA category, one i2i sample, one real
normal conversion, one Marigold input, and one `--max_samples 1` inference
before launching all categories. The Marigold and Open3D stages are expected
to be numerically stable up to normal CUDA floating-point nondeterminism; exact
byte equality across different GPU architectures is not required.
